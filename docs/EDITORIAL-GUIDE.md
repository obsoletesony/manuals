# Editorial guide

Start with what the reader needs to do. Use prose until another format makes the
instruction materially clearer.

## Voice

- Write directly and confidently.
- Prefer short, natural sentences.
- Tell the user what happens.
- Avoid defensive AI-style reassurance.
- Avoid terms such as "bounded," "collision-safe," "best effort," and "safe
  fallback" unless the term is technically necessary.
- Leave out implementation details that do not help someone use the product.
- State a fact once. Do not repeat it across sections.
- Do not use a running header that simply repeats the page title.
- Do not pad a manual to make it look comprehensive.

## Structure

- Organize the manual around tasks the reader needs to complete.
- Combine sections that cover the same action.
- Put controls beside the feature they control.
- Add a contents page only when it improves navigation.
- Use callout boxes sparingly.
- Keep requirements and compatibility in one clear section when possible.
- Keep troubleshooting focused on problems users are likely to encounter.

## Visuals

Add a visual only when it explains something materially better than a short
paragraph or compact table. Useful cases may include:

- the location of a physical button or hardware part;
- file or folder placement where spatial hierarchy matters;
- a sequence that is genuinely difficult to follow in prose;
- a comparison with several exact mappings;
- a screenshot needed to identify a specific screen or control.

Do not add a visual for:

- a single directional copy operation;
- a short installation path that fits in one code block;
- a simple supported or unsupported statement;
- an internal audio or software pipeline;
- decorative balance or empty-space filling;
- a visual quota or an official appearance.

Charts require real numeric data and a specific question they help answer. Do
not create chart placeholders.

For every proposed visual, ask:

> Would removing this make the instructions harder to understand?

If the answer is no, remove it.
